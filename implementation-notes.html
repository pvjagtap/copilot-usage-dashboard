v1.10.91 — Usage-by-Model vs hero drift (Aug 15, 2026)

Symptom: the Usage-by-Model TOTAL row showed 102,462.90 while the hero "AI Credits Spent" tile, the AIC card and Usage-by-Source all showed 98,450.30.

Design decision — one credit basis, not two

The extension had two independent credit computations reading the same scan: creditEntries (per llm_request, feeding computeSummary → the hero) and sessionCreditsMap in computeSessionViews (per turn, feeding the tables). The second one diverged in four ways: it collapsed a turn to debugAicCredits whenever that was non-zero (dropping rate-estimated requests inside partially-reported turns), rate-estimated at the parent turn's model rather than per sub-model, applied no billable filter, and pinned the whole session lifetime to session.lastDate.

Rather than patch the four symptoms, SessionView.aicCredits is now derived from creditEntries after computeSummary runs. Reconciliation is structural, not arithmetic — there is no second formula left that can drift.

Deviation — aicByDay is not cycle-clipped

summary.byDay drops anything outside the current billing cycle (correct: it answers "what will GitHub bill me this cycle"). SessionView.aicByDay deliberately keeps every AIC-era day, because the dashboard's historical month ranges are rendered from session data — clipping it would zero out July, June, etc. exactly as the pre-existing note in computeSessionViews warns.

Tradeoff — the "Other sources & live" row

The hero includes billable credits with no owning chat session: in-flight OTel requests not yet flushed to a debug log, and OMP / Pi / CLI agent sessions. Options considered:

OptionVerdict
Subtract agent credits from the hero so the table matchesRejected — the hero must equal what GitHub bills, which includes agent usage.
Relabel the TOTAL row "VS Code sessions only"Rejected — leaves the user doing arithmetic across three cards to check one number.
Render the remainder as its own row (chosen)TOTAL equals the hero exactly; the remainder is visible and labelled instead of hidden.

Its value is computed as rangeAicTotal − Σ model rows rather than from unattributedByDay directly. That makes it absorb any residual by construction, so the TOTAL row cannot silently disagree with the hero again — including credits from sessions whose lastDate falls outside the selected range.

Open questions

  • The dashboard's session filter (DATA.sessionsAll.filter(... s.lastDate ...)) still selects sessions by lastDate. A session that ran in August but last spoke in September is excluded from the August table entirely; its August credits land in "Other sources & live". Should the filter switch to "has credits in range"? That would change session counts and token totals across every chart, so it was left alone — confirm whether you want that too.
  • verify-no-drift.js, verify-dashboard-vs-api.js and verify-live-aic-reconciliation.js fail identically before and after this change (the last one is a missing vscode stub in the harness). Pre-existing failures, not regressions.

Issue #5 — Usage statistics don't match actual numbers from GitHub

Report: github.com/pvjagtap/.../issues/5

User sees 7,347.7 credits in the extension vs 5,278.2 credits reported by GitHub. Subtracting the user's Ollama line (1,662.33 credits) leaves 5,685.4 — close but still ~407 over.

1. Root-cause analysis

1a. Bug — Non-GitHub models (Ollama, BYOK, local) counted as billable (primary)

VS Code's chat & agent surfaces emit OpenTelemetry traces for every model invocation regardless of backend — including Ollama, LM Studio and any "Bring Your Own Key" provider. Our OTLP receiver (src/otelReceiver.ts) ingests them all. In buildDashboardData() any request without copilotUsageNanoAiu (which only GitHub's backend emits) falls back to a rate-table estimate that defaults to gpt-4.1 (200 / 800 credits per 1M tokens) when the model name isn't recognised. The result: Ollama traffic shows up as "AIC credits" and inflates the total.

Confirmed by GitHub's billing docs:

"Code completions and next edit suggestions are not billed in AI credits."
"Copilot features that use AI models consume AI credits" — i.e. only features routed through GitHub's billing backend; BYOK/local models are paid for by the user's own provider key.

1b. Bug — totals span from AIC effective date, not the current billing cycle (secondary)

dashboardData.ts filters aicTurns with t.timestamp.slice(0,10) >= AIC_EFFECTIVE_DATE (= "2026-06-01") and computeSummary() sums every entry it receives. For users whose billing cycle starts mid-month (e.g. signup-anchored cycles), or once we cross into July, the dashboard will keep counting credits beyond the current cycle — so the "monthly budget" reading is wrong.

1c. Gap — Auto-model 10% discount not modelled (minor)

GitHub's doc: "If you are on a paid Copilot plan, you qualify for a 10% discount on model costs while using auto model selection." When copilotUsageNanoAiu is present this is already baked into the billed value. Only the rate-table estimate path misses it. Left as a follow-up because the API-billed value dominates the realistic case.

2. Solution design

2a. "Billable" classifier (the single source of truth)

A credit entry is treated as billable iff either:

  1. It carries an explicit copilotUsageNanoAiu > 0 (= GitHub's backend already billed it), or
  2. Its model name matches an entry in DEFAULT_MODEL_COSTS (a known GitHub-Copilot-supported model), and the model is not in the user-configured excludeModels list.

Everything else (Ollama, LM Studio, BYOK keys, unknown custom models with no nanoAiu) is non-billable — surfaced in the dashboard as an "informational" section but excluded from totalCredits, the budget bar, overage cost, projected total, and the daily-limit guard.

2b. Cycle-window scoping

AICCalculator.computeSummary() now filters every entry to the current billing cycle window (billingCycleStart … billingCycleEnd inclusive). This aligns "dashboard total" with "what GitHub will charge you this month".

2c. New settings

SettingDefaultPurpose
copilotUsage.aic.includeOnlyBilledModels true Master switch. When true (recommended), non-billable models are listed but excluded from totals.
copilotUsage.aic.excludeModels [] Explicit user-supplied substrings to force-exclude (e.g. ["my-internal-llm"]).
copilotUsage.aic.extraBilledModels [] Model substrings to treat as billable even without a rate match (escape hatch for previews).

3. Deviations & trade-offs

  • No name-pattern allow/deny list for BYOK (e.g. no hardcoded /ollama/i). Rationale: the presence of copilotUsageNanoAiu plus the rate-table membership is a sharper signal than provider-name guessing. Avoids false positives like the legitimate raptor-mini fine-tune.
  • Non-billable credits are still estimated and shown (in their own table) so users can see how much their local-model traffic would cost on Copilot — useful for capacity planning. Just not summed into the billed total.
  • 10% auto-discount on rate-estimates not yet applied; the API-exact path already reflects it. Tracked as a follow-up — small effect.

  • Should auto-detect-plan also flip includeOnlyBilledModels on/off? Currently the new setting is plan-independent.

8. Research — Standard ways to scope "GitHub-billable" usage from logs

Follow-up to issue #5: the v1 fix relies on a substring match against the built-in DEFAULT_MODEL_COSTS rate table as the default arbiter. That heuristic is fragile (new preview models look "unknown" until the table is updated by hand; a BYOK model ID can accidentally substring-match a known family). The question we set out to answer was: what authoritative, documented signals could we use instead?

8a. Signal inventory — ranked by reliability

8b. Signals we looked for but that are not in the debug log

Verified by dumping every attrs.* key on a real llm_request entry from a current debug log. The complete attribute set is: model, debugName, inputTokens, outputTokens, cachedTokens, ttft, responseId, userRequest, inputMessages, maxTokens, requestOptions, requestShape, copilotUsageNanoAiu, systemPromptFile, toolsFile. There is no byok, vendor, endpoint, customModel, or provider hint — so at the debug-log level copilotUsageNanoAiu presence is the only direct signal of GitHub billing. The good news: the Copilot extension only ever writes its own debug log, so every llm_request entry in that file is already scoped to Copilot traffic. Local Ollama / LM Studio called via a different extension never appears there at all.

8c. Why this changes the OTel path too

The OTel receiver listens on 127.0.0.1:14318 — the endpoint the Copilot Chat extension is configured to push to. Spans follow the OpenTelemetry GenAI semantic conventions (gen_ai.request.model, gen_ai.usage.prompt_tokens, …). Crucially, no byok / vendor / billing.multiplier attribute is present on the span — that determination happens later when the API response comes back. So if a user has configured Ollama as a BYOK model inside Copilot Chat itself, the OTel exporter ships a regular GenAI span with the Ollama model id, and the old heuristic had no way to know GitHub didn't bill it. The catalog lookup fixes this: any model id that lives under a non-copilot provider in the CDN manifest (or returns multiplier === 0 from CAPI) is now classified as non-billable up-front, regardless of substring matches against the rate table.

8d. Updated classifier precedence (v1.10.12)

1. config.excludeModels         → force NON-billable
2. hasActualCredits === true    → force billable (nanoAiu from GitHub)
3. config.extraBilledModels     → force billable
4. includeOnlyBilledModels===false → everything is billable (legacy mode)
5. online catalog lookup    → use entry.billable (CAPI > CDN)
6. calculator.isKnownGHCModel() → fallback rate-table heuristic
7. otherwise                    → NON-billable

8e. New setting

copilotUsage.aic.useOnlineModelCatalog (boolean, default true) — gates rule #5. When disabled, the extension operates fully offline using only the built-in rate table (the v1.10.11 behaviour). The catalog is cached for 24h in globalState, hydrated synchronously at activation, then refreshed in the background. Both fetches are best-effort and silent on failure.

GitHub Copilot CLI (@github/copilot) Live Usage Integration

Goal: add the standalone Copilot CLI as a fourth source alongside VS Code chat sessions, Oh My Pi, and Pi — with the same billing-period filter, the same shared AIC budget, and the same per-source column in the dashboard.

Design decisions (where the spec was ambiguous)

DecisionWhat we choseWhy
Which signal is authoritative for AIC? Hybrid: session.shutdown.data.modelMetrics.{m}.requests.cost when present, else live-walk estimate (prompts × multiplier). The diagnostic in tests/diagnose-copilot-cli.mjs found 4 of 8 sampled sessions had no session.shutdown event (crash, Ctrl-C, still-open). Ledger-only would silently drop ~50% of CLI activity. Live-only is ~5% imprecise on clean sessions because it can't see the CLI's actual rounded cost. Picking the per-model winner reconciles to the GitHub bill on shutdown sessions and recovers ~50% of otherwise-invisible spend on the rest.
Which model do we attribute a prompt to? assistant.message.data.model (most-recent response), falling back to session.start.selectedModel only before the first response of the session lands. Two sampled sessions selected claude-haiku-4-5 in the UI but session.shutdown showed claude-sonnet-4.6 was actually billed (silent fallback / routing). The assistant-side model reflects what GitHub bills.
How is the multiplier resolved? classifyByCatalog(model).multiplier (CAPI live data) wins; built-in FALLBACK_MULTIPLIERS table covers the first scan before the catalog finishes loading. Re-uses the same authoritative source the rest of the extension uses for billable classification — no duplicate rate table to drift out of sync. The fallback table mirrors what's published at docs.github.com/en/copilot/concepts/billing/copilot-requests.
How do CLI credits enter the calculator? creditEntries.push({ actualCredits, billable, model, … tokens: 0 }) — same path OMP/Pi take when they have a known credit value. The CLI bills per prompt × multiplier, not per token. Token fields stay at 0 so they don't inflate the input/output credit subtotals; the calculator sees only the final AIC number.
Slash-command filter Strict regex /^\/[A-Za-z][\w-]*\b/ after trim. Loose startsWith('/') would have matched filesystem paths a user pastes for context (/usr/local/bin/…), undercounting billable prompts.
Reconciliation residual vscodeAicCredits = total − omp − pi − cli The four source columns must sum exactly to the headline AIC total — same invariant the OMP/Pi columns already satisfy.

Deliberate non-additions

  • We do NOT read ~/.copilot/usage.db. Inspection confirmed it indexes VS Code chatSessions (workspaceStorage/…/chatSessions/*.jsonl) — the same source scanner.ts already walks. 0/14 overlap with CLI sessions in the sampled vault. Reading it would cause double-counting.
  • We do NOT read ~/.copilot/session-store.db. It's lazily populated by /chronicle reindex, mostly empty in normal use, and carries no AIC field that isn't already in events.jsonl.
  • We do NOT extend AICCalculator with a prompt×multiplier code path. The existing actualCredits override is already the right primitive — same model OMP/Pi use. Adding a parallel path would create two ways to do the same thing.

Tradeoffs & alternatives considered

  • Ledger-only. Cleaner code, but rejected: the diagnostic proved we'd silently lose half the activity.
  • Live-only. Simpler too, but rejected: when GitHub actually publishes a precise per-session cost, we should honour it instead of substituting our estimate.
  • Treat selectedModel as truth and only show drift to the user. Rejected after seeing the haiku-selected / sonnet-billed sessions in real data — that would over-bill the cheaper model and under-bill the more expensive one. Always attribute to the model that actually answered.
  • Add a fifth source column "BYOK". Out of scope — the existing non-billable models panel already surfaces local Ollama / BYOK runs separately from the billed total.

Open questions

  • Roaming events.jsonl rotation. CLI does not appear to rotate / compact session files. If the file grows multi-MB, the line-by-line re-parse on mtime change will be slow. Current mitigation: 16-way concurrent reads + per-file mtime cache. If we see real-world performance issues, we'd add a tail-only parser that remembers byte offset.
  • Resume-after-shutdown semantics. If a session emits a session.shutdown then a session.resume and more prompts, we accumulate the second shutdown's cost on top of the first (per-model addition). The diagnostic shows this is the intended CLI behaviour, but if GitHub changes how cost is reported on the second shutdown (delta vs cumulative) we'd need to revisit.
  • Silent-reroute over-count. When a session has BOTH a live haiku prompt and a sonnet ledger entry (observed in 2/8 audited sessions — GitHub silently rerouted the model), the per-model hybrid total keeps the haiku live estimate (0.33 AIC) and the sonnet ledger (e.g. 2.0 AIC), so we report 2.33 when GitHub only billed 2.0. Decided to keep the over-count visible rather than silently absorb the haiku prompt — the driftAic field surfaces the delta and lets users investigate. Alternative considered: drop live-only models when hasLedger is true. Rejected because it would hide the routing decision entirely.

Audit pass (post-implementation)

The implementation was audited against the real C:\Users\Jagtprit\.copilot\ vault and a synthetic test fixture. Audit suite at tests/verify-cli-scanner.js — 67 assertions across 4 parts. The audit found 2 real bugs the initial implementation review missed, both now fixed:

  • Bug 1 — slash-command filter dropped filesystem paths. The regex ^\/[A-Za-z][\w-]*\b matched /usr/local/bin/node because \b fires between r and /. User prompts that started with a Unix path were silently excluded from billable counts. Fixed to ^\/[A-Za-z][\w-]*(?:\s|$) — require whitespace or end-of-string after the first token.
  • Bug 2 — session.model_change had no effect on attribution. The handler only updated uiSelectedModel, which is the fallback source. Because lastAssistantModel (set by the prior assistant.message) still won, an explicit user model switch did not take effect until the next assistant response landed — silently mis-attributing the very next prompt. Fixed to update both signals so model_change becomes the immediate ground truth.
  • Latent bug 3 — double-count of paired session formats. 9 of 14 active session IDs in the real vault existed in BOTH <id>.jsonl (legacy flat) AND <id>/events.jsonl (new format). The original enumerateSessionFiles would have visited both. Never reached production because all paired sessions happened to have empty new-format files, but would have triggered the next time the CLI emitted to both. Fixed: mtime-based de-dup with Map<sessionId, Candidate> + zero-byte skip.

Final audit result: 67/67 assertions pass. Real-vault coverage: 23 sessions parsed, 51 billable prompts, 60.99 AIC, 51,103 output tokens, 8 ledger-reconciled / 15 live-only. The scanner's all-time aggregates match an independent re-walk byte-for-byte (Part C.12), and per-session results agree with tests/diagnose-copilot-cli.mjs.

User report (verbatim):

why in the world i am seeing the 0.00 AIC Session all the time — and later: why the heck we are dropping to zero when we should not and should show accurate information / do the code diff since release before yesterday and current code changes and fix all the issues

Symptom: Dashboard sidebar showed AIC (LAST REQ) = 3.98 and AIC (SESS) = 0.00, while the Live OTel by Model table directly below it listed gpt-5.3-codex: 12.07 AIC and claude-opus-4.7: 58.89 AIC (summing to 70.96). Root cause — two compounding bugs in the v1.10.13 release

  1. Hardcoded hasActualCredits=false in the classifier call (src/dashboardData.ts post-processor): 
    isBillable: classifyModelBillability(calculator, config, row.model, false, classifyByCatalog),
    The classifier's precedence has a rule #2: "if the row already has authoritative GitHub-billed credits, it's billable". Hardcoding false meant the rule never fired, so classification fell through to the catalog lookup. When the user's chatLanguageModels.json listed the same id under a non-Copilot vendor (Copilot Chat itself surfaces Anthropic-backed routed models with vendor: "anthropic"; users with real BYOK Anthropic keys trigger the same map), classifyByCatalog() demoted the row to non-billable and the post-processor's filter stripped sessionAIC to zero. The per-model table still rendered the real billed aicCredits values because the table's row aicCredits field is set upstream from authoritative copilotUsageNanoAiu data — only the post-processor's reclassification + filter was broken.
  2. Status-bar tooltip hid the session line at 0.00 (src/statusBar.ts line 209): 
    if (data?.currentSessionAIC) { lines.push(...) }  // truthy check, omits 0.00
    Made the demotion bug above invisible. Users only saw last request and concluded the dashboard was broken.

Fix — pass evidence-based provenance instead of a hardcoded literal

Relationship to the classifyByCatalog() precedence fix

A prior session added a complementary fix in src/modelCatalog.ts that makes CAPI billable: true override the BYOK alias inside the catalog lookup itself (precedence rule #1 promoted, BYOK demoted to rule #2, CAPI billable: false kept at rule #3). The two fixes are belt-and-suspenders:

  • Catalog fix: if CAPI knows the model id is billed on this plan, the catalog returns billable=true and the BYOK alias is ignored. Works even when there's no debug-log evidence (e.g. an OMP/Pi session that wasn't routed through GitHub's debug-log producer).
  • hasActualCredits fix (this release): if any contributing request carried a GitHub-billed copilotUsageNanoAiu, that is direct evidence the row is Copilot-billed — overrides catalog regardless of CAPI's coverage (handles preview models like gpt-5.3-codex that may not yet be in CAPI's /models response).

Either signal alone is sufficient to keep the row counted. Both must return non-billable for the row to be filtered out, which is the right contract for the user's "I have BYOK plus Copilot" mixed environment.

Design decisions / deviations from naive fix

DecisionRationale
Track hasActualCredits per row, not as a global flag. The user can have some models billed by GitHub and other models served locally in the same session. A global flag would either let Ollama leak into billable (reintroducing issue #5) or strip legitimate GitHub-billed credits.
Set hasActualCredits=false for pending OTel-only estimates even though their aicCredits > 0. Pending values are rate-table extrapolations, not GitHub's billed amount. Marking them as actual would defeat the safety contract: the classifier is supposed to use hasActualCredits as evidence, not as a "this row has a non-zero credit number" check.
Always recompute sessionAIC in the post-processor, not just when includeOnlyBilledModels is on. Previously the recompute was gated. 13. Dynamic per-model pricing (July 2026) DONE

Problem

Three independent hardcoded pricing tables drifted apart because they were only updated when GitHub announced new models:

  1. DEFAULT_MODEL_COSTS in src/aicCredits.ts — per-1M input/output/cache rates.
  2. FALLBACK_MULTIPLIERS in src/cliScanner.ts — legacy per-prompt multipliers.
  3. KNOWN_MULT in src/dashboardPanel.ts — a third multiplier copy inside the webview.

Six models VS Code's own Language Models view was already pricing were absent from all three tables: claude-sonnet-5, gpt-5.6-{luna,sol,terra}, gemini-3.6-flash, and mai-code-1-flash. Any of these routed through the extension was silently priced at GPT-4.1's fallback rate (200 in / 800 out per 1M).

Design decision — CAPI-first, three-tier fallback

The Copilot CAPI /models endpoint (which the extension already calls to determine billability) is the same source VS Code's built-in "Language Models" view reads its per-1M cost columns from. We extended the existing catalog to also parse the per-token rates and made the rate-lookup chain read: 

1. Live CAPI catalog via getRatesFor()  ← authoritative, self-updating
2. Static DEFAULT_MODEL_COSTS           ← offline emergency net
3. Hardcoded GPT-4.1 default            ← final fallback

Deviations from the initial plan

  • The initial plan assumed the CAPI response would carry billing.price with a fixed field shape. Because we couldn't verify the schema without a live network call, CapiPriceShape defensively accepts three container names (price | rates | pricing) and three spellings per field (input/in/input_tokens, etc.). extractRatesFromCapi() tolerates whichever CAPI actually emits — no code change needed if the field name flips.
  • A one-shot diagnostic log line in fetchCapiModels() dumps the first entry's billing block so we can confirm the real schema from any user's log rather than guessing.
  • The initial plan said to delete FALLBACK_MULTIPLIERS wholesale. We did — but the existing CLI-scanner test asserted specific values through that table. Rather than deleting the assertions, we updated the test to seed the catalog directly, which now exercises the new resolver path instead.
  • Similarly, KNOWN_MULT in the webview was deleted and replaced by a DATA.modelMultipliers snapshot pushed from the extension side (populated from the live catalog in buildDashboardData()).
  • Added hyphen↔dot normalization to classifyByCatalog() — CAPI publishes ids as claude-haiku-4.5 but OTel and CLI logs report claude-haiku-4-5. Both forms now resolve.

Tradeoffs

  • Rate-derived multiplier vs "1". When the catalog knows the per-1M rates but not the per-prompt multiplier, we derive it as max(0.25, inputCreditsPerMillion / 250) where 250 is GPT-4o's baseline rate. This is a rough proxy but strictly better than the previous "just return 1" behavior. Cap at 0.25 prevents underflow for very cheap models.
  • Kept DEFAULT_MODEL_COSTS as fallback. Considered trimming to 5 ids as the design proposed, but leaving the full table is cheap (~40 lines) and gives us offline resilience during the ~200ms activation window before the CAPI catalog resolves. It only wins when the catalog is missing OR missing rates for a specific model, so drift risk is bounded.

Model resolution — family fallback (1.10.74)

The claude-opus-5 — base — 0.00 row was not display noise; it was the visible symptom of a resolution failure. claude-opus-5 was absent from DEFAULT_MODEL_COSTS, so with the live CAPI catalog unavailable findModelRate() returned null and three things broke at once:

calculateCredits()Applies the gpt-4.1 default: 200/800 per 1M instead of 500/2500.

  • Design decision: Fall back by family, not by nearest-string. An unmatched id is split into family + version tail + optional variant, and inherits the newest table entry sharing that family and variant — gpt-5.7-codex takes gpt-5.3-codex, not gpt-5.5. Rates and tier are borrowed; the observed id is kept for display so the table never claims the user ran a model they did not.

Catalog refresh — miss-driven instead of TTL-driven (1.10.75)

Prompted by the question "why don't we just cache once and update only when something changed?" The answer is that we already cache correctly — the gap was when we decide something changed.

What the catalog already did, and still does: persists in globalState under copilotUsage.aic.modelCatalog.v1; hydrates synchronously at activation before any network call; survives restarts and extension upgrades; serves the stale snapshot while a refresh runs; and discards a refresh that produced zero entries rather than overwriting a good snapshot. It is a write-on-success store, not a per-session fetch.

What was wrong: CATALOG_TTL_MS gated refreshes purely on age. A snapshot taken at 09:00 is "fresh" for the rest of the day, so a model GitHub enables at 14:00 is invisible until tomorrow. The cache is a snapshot of a set that grows without notice, so age is simply the wrong signal.

  • Design decision: The right signal is a resolution miss. If neither the live snapshot nor the static rate table can resolve an observed id, that is direct evidence the snapshot predates a shipped model. notifyUnknownModel() is called from findModelRate() at the point it falls through to the family fallback, and forces a refresh out of band.
  • Design decision: Placed the call at the family-fallback boundary rather than right after the getRatesFor() miss. The earlier position would fire for every model the static table already prices correctly, which is noise; the later position fires only for ids nothing knows.
  • Design decision: refreshCtx is captured inside loadCatalog() rather than threading an ExtensionContext down through AICCalculator. findModelRate() is called per credit entry from several call sites; giving all of them a context purely to enable a refresh would be a large change for a side effect.
  • Tradeoff: Three independent debounces, because findModelRate() runs thousands of times per scan: one report per id per session, one refresh in flight at a time (runRefresh(), which now also guards the activation path that previously could overlap), and a hard floor of 15 minutes on snapshot age. The age floor does double duty — it is also what stops local and BYOK ids from retriggering fetches. Those are never in CAPI, so no refresh will ever resolve them, and without the floor every new Ollama model would cost a round trip.
  • Tradeoff: A brand-new model is still mispriced for up to 15 minutes plus the refresh latency. Accepted: the family fallback covers that window with a sibling's rate and, critically, the correct billable verdict, so the visible error is a rate approximation rather than spend disappearing from the billed table.
  • Deviation: A miss with no snapshot at all (cold start, offline, failed token mint) deliberately does nothing — loadCatalog() already has a refresh in flight in that state, and firing a second one would just race it.
  • Open question: The 15-minute floor is a guess, not a measurement. If GitHub's model set turns out to churn faster than that in practice it should come down; if BYOK-heavy users report refresh chatter it should go up. Worth revisiting once there is telemetry on how often notifyUnknownModel() actually fires.

2. Two-window AIC drift + startup double-counting (2026-08-04)

User ran two separate VS Code windows on the same PC, each with its own workspace open, and saw two different AIC credit totals for the same billing cycle. Separately, one window briefly showed a number roughly double the eventual figure right after cold start, which corrected itself the moment the user sent a chat message.

2a. Ruled out — cross-window / Settings Sync state

src/machineSync.ts publishes a per-machine rollup to globalState (MACHINES_KEY), read-modify-write, keyed by vscode.env.machineId. Two windows on the same PC share the same machineId and the same profile's globalState store, so they write to the same slot — there is no way for this to double a total. More importantly, the combined/cross-machine figure (DashboardData.combinedCycleCredits and DATA.machines) is never read by the hero KPI cards or the "AI Credits (AIC) — Usage-Based Billing" section — dashboardPanel.ts only renders the per-machine "Systems" table when machines.length > 1 (i.e. a genuinely different machine has reported), and that table is explicitly documented as informational-only, separate from the machine-local headline numbers. Confirmed by grepping for combinedCycleCredits/.machines across every UI file. This was the user's own working theory; it does not hold up against the code.

2b. Actual cause — cold-scan race with in-flight Copilot Chat writes

Both windows independently scan all of workspaceStorage on disk (by design, so the dashboard reflects total usage regardless of which window is open — see ARCHITECTURE.md). Each extension host keeps its own in-memory, per-process mtime cache (_sessionBundleCache / _debugLogCache in scanner.ts); nothing is persisted or shared across windows or restarts. scanner.ts already dedupes the known case of a chat-session file containing multiple rows for the same (sessionId, turnIndex) — an empty in-progress row plus the fully-populated row written once a turn settles (the turnByKey map, added after a prior +1,869-phantom-credit incident, see tests/verify-no-drift.js). That dedup can only work on rows that have already landed on disk. If a window's cold activation scan (await runScan() in extension.ts activate()) happens to run at the exact instant another window's Copilot Chat turn (or subagent chain) is mid-write, it can observe a transient, not-yet-settled duplicate and over-count it once. Running two windows makes this more likely simply because there are more workspaceStorage folders and more concurrently-active Copilot processes to catch mid-write. Sending a new message doesn't fix the old duplicate directly — it triggers the debug-log file watcher (fireDebugLogScan → runScanSerialized), which rescans everything, and by then VS Code's own chat storage has settled/compacted the previously in-flight file, so the recount comes out correct.

2c. Fix applied

Added a one-shot "settle" rescan ~5s after the initial activation scan in extension.ts (activate()), disposed via context.subscriptions. This re-runs runScan() and refreshes the status bar / dashboard once more shortly after cold start, so a transient duplicate from 2b self-corrects automatically instead of requiring the user to send a message first.

  • Design decision: 5s was chosen as a reasonable window for an in-flight turn to finish writing without meaningfully delaying anything the user cares about (the initial scan already renders immediately; this is a silent follow-up).
  • Deviation: This does not eliminate the race, only shrinks the window in which a user could see a stale/inflated number after cold start. A pathological case (a turn still streaming 5+ seconds after the window's own activation) would still show a transient number until the next debug-log write or periodic rescan.
  • Open question: If this proves insufficient in practice, a more robust fix would be cross-referencing child_session_ref completeness before counting a session as final, but that is a larger change to the scanner's session-bundling logic and wasn't warranted for a single report.
